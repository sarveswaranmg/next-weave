The NeuroWeave Handbook

What got built across two sessions, how the pieces fit together, and the exact steps to self-host, verify, and test all of it — for free.

MIT licensed 254 tests passing · 12 Alembic migrations · Last updated 2026‑08‑26

01What we built

NeuroWeave already had a working cognitive memory engine — structured extraction, semantic consolidation, an identity graph, predictive recall, all wired behind one RuntimeOrchestrator.chat() pipeline and a multi-tenant FastAPI server. Two things were missing before it could go from “a project you run” to “a memory layer other people can adopt or you can host for others”: an an install experience as easy as pip install, and a way for people to actually get access without you running a script for each one. Both got built.

Embedded mode

pip install and go — no server.

  • New neurowave.Memory class runs the full pipeline in-process against local SQLite
  • Core package renamed app/ → neurowave_engine/ so it can be imported without colliding with your own app/
  • Dependencies split into a lean core vs. a server extra

Self-serve signup

Host it once, let others get their own key.

  • Public /signup page: email → verify → API key, shown once
  • Hard usage cap per signup tenant, checked before the LLM call runs
  • IP rate limiting, no account-enumeration, no billing yet

Both sit on top of the same engine and the same Tenant / ApiKey / User auth model that was already there — neither one is a fork or a parallel system.

02How it works

The pipeline

Every chat turn, embedded or hosted, runs the same sequence:

Ingest→ Score→ World model→ Recall→ Compose context→ LLM call→ Store response

Scoring is heuristic, not an LLM call — the design principle throughout this codebase is that a live request never waits on an LLM call it doesn’t strictly need. Expensive batch work (semantic consolidation, memory evolution, “dream mode” offline replay) is scheduled separately rather than run inline.

Two ways to run the same engine

EmbeddedServer
Entry pointneurowave.Memory()CognitiveAgent / REST
StorageLocal SQLite filePostgres
Background jobsNone (synchronous only)Celery + Redis
TenancyOne implicit local tenantMany, isolated by API key
FitsA script, a notebook, one processA product other people/services call

Multi-tenancy and the signup layer

Every hosted request authenticates to one ApiKey, which resolves to one tenant_id. Every user_id in a request must belong to that tenant — that’s what stops one customer from reading another’s data. The signup flow just adds a second, public way to create a Tenant: tenant.email_verified_at is set only when someone verifies through /signup, which is also exactly the flag that decides whether usage caps apply to them (more on that next).

03Self-hosting is free

NeuroWeave is MIT licensed. There is no paid tier of the software itself, no license key, and nothing in the codebase phones home. Running your own instance costs exactly two things: whatever server you put it on, and whatever your own OpenAI/Google/Anthropic keys cost you for the calls you actually make.

Fixed while building this

The usage cap added for self-serve signup was originally wired to every /runtime/chat call, which would have capped your own tenant at 200 calls/month too. It now only applies to tenants that verified through the public /signup page — a tenant you create for yourself with scripts/bootstrap_tenant.py is never capped, tracked, or throttled. Self-hosting for yourself or your team has no artificial ceiling.

The free-tier cap only exists for the scenario where you choose to run a public signup page and let strangers create their own tenants under your infrastructure — it protects you, the operator, from an open door driving up your LLM bill, since there’s no billing integration (yet) to make strangers pay their own way. If you never expose /signup, or only ever create tenants yourself, this cap never engages.

04Ways to deploy

A. Embedded — no deploy at all

For a script, notebook, or a single process that just needs memory. Nothing to host.

# from a NeuroWeave checkout
pip install -e .
pip install -e "sdk/python[embedded]"
from neurowave import Memory
m = Memory()  # ./neurowave.db on first use
m.chat(user_id="alice", message="I use FastAPI and PostgreSQL.")

B. Self-hosted server — Docker Compose + Caddy

The path this handbook walks through below. One server, automatic HTTPS, Postgres + Redis + Celery for the full pipeline including background consolidation. This is what docker-compose.prod.yml is built for.

C. Kubernetes

Manifests already exist under k8s/ for a cluster deployment — see k8s/README.md. Same engine, same image, just a different orchestrator.

05Self-host it, step by step

This is the Docker Compose + Caddy path (option B above), aimed at a real server with a domain. Everything here also works verbatim on your own machine for a dry run first — set DOMAIN=localhost and Caddy issues itself a local certificate instead of requesting one from Let’s Encrypt.

  1. Provision a server and point DNS at it

    Any small Linux VPS works. Create an A record for your domain pointing at the server’s public IP before starting Caddy — it needs that to succeed at the Let’s Encrypt ACME challenge.

  2. Install Docker + Docker Compose, open ports 80/443

  3. Clone the repo and create .env.prod

    cp .env.prod.example .env.prod

    Fill in, at minimum:

    DOMAINYour real domain (or localhost for a dry run)
    OPENAI_API_KEYRequired — embeddings always go through OpenAI
    GOOGLE_API_KEYOptional — the default chat provider (free tier); without it, chat falls back to echo
    POSTGRES_PASSWORDopenssl rand -hex 32
    CREDENTIAL_ENCRYPTION_KEYpython -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
    SMTP_*Real creds if you want /signup’s verification email to actually send — leave blank to see the link in the container logs instead

  4. Build and start the stack

    docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build

  5. Run migrations

    docker compose -f docker-compose.prod.yml --env-file .env.prod exec neuroweave \
  alembic -c migrations/alembic.ini upgrade head

  6. Get your first key

    Two ways — use whichever matches how you plan to use this deployment:

    # For yourself: no usage cap, ever
docker compose -f docker-compose.prod.yml --env-file .env.prod exec neuroweave \
  python scripts/bootstrap_tenant.py --name "My Company" --email me@example.com

# For others: visit the page, or drive it from the command line
open https://$DOMAIN/signup

  7. Verify end-to-end

    curl https://$DOMAIN/runtime/health

curl -X POST https://$DOMAIN/runtime/chat \
  -H "Content-Type: application/json" \
  -H "X-API-Key: nw_live_..." \
  -d '{"user_id": "00000000-0000-0000-0000-000000000001", "message": "hello", "provider": "echo"}'

    Expect a 200 with an echoed response. Swap provider to "google" once you’re ready to use a real model.

If you plan to open /signup publicly

The IP rate limiter only sees real caller IPs if uvicorn trusts Caddy’s X-Forwarded-For header — docker-compose.prod.yml already runs uvicorn with --proxy-headers --forwarded-allow-ips='*' for this, which is safe specifically because Caddy is the only public entry point (no host port mapping on the app container). Don’t remove that flag without also exposing the app container directly, or every signup will appear to come from Caddy’s own IP.

06Testing

Everything below runs against local SQLite — no Docker, no real API calls, no network. Fast enough to run before every change.

# from the repo root, with the venv activated
DATABASE_URL="sqlite:///./ci_test.db" OPENAI_API_KEY=sk-test LOG_LEVEL=INFO \
  .venv/bin/python -m pytest tests/ sdk/python/tests/ -q

254 tests, in around 45 seconds: the core engine, auth/RBAC, the embedded Memory SDK, and the signup/usage-cap flow (email verification, single-use tokens, IP rate limiting, the cap applying only to self-serve tenants).

Manually exercising signup, without a real server

Useful for confirming the flow works before you have SMTP configured — the verification link just prints to the log instead of being emailed.

uvicorn neurowave_engine.main:app --reload
# in a browser: http://localhost:8000/signup
# submit the form, then check this terminal's log for:
#   Verification link for you@example.com: http://localhost:8000/signup/verify?token=...
